# **ETAPA 2.6 — MGH™ PILOTO 1.0**

## **1. Objetivo do Piloto 1.0**

O primeiro piloto não existe para provar que o MGH funciona.

Existe para responder perguntas como:

As pessoas compreendem os itens da maneira esperada?
As respostas realmente discriminam pessoas?
Existem alternativas escolhidas por quase todo mundo?
Existem itens redundantes?
Os construtos aparecem com cobertura equilibrada?
O resultado produzido faz sentido quando confrontado com comportamento observado?
Quanto tempo a aplicação leva?
Onde há inconsistências?
Quais itens precisam sair?

Portanto:

**Piloto 1.0 = instrumento de investigação.**

Não produto comercial definitivo.

# **2. Quantidade: proponho 48 itens**

Depois de tudo que construímos, **48 continua sendo um excelente ponto de partida**.

# **4. Mas não usaremos 12 escolhas forçadas iguais**

Quero testar duas metodologias dentro do piloto.

### **8 itens de escolha forçada**

Exemplo:

Qual recurso tende a ajudá-lo primeiro?

A / B / C.

### **4 itens de avaliação independente**

Exemplo:

Ao compreender um processo novo, indique quanto cada recurso costuma ajudá-lo.

**Visualizar um fluxo**1 — pouco ... 5 — muito

**Ouvir uma explicação**1 ... 5

**Experimentar o processo**1 ... 5

Por quê?

Porque depois poderemos comparar:

**preferência relativa × intensidade declarada.**

Imagine alguém escolhendo visual em 6/8 itens, mas dando:

Visual 5
Auditivo 4,8
Cinestésico 4,6.

Isso conta uma história diferente de alguém com:

Visual 5
Auditivo 2
Cinestésico 1.

No sistema exclusivamente forçado, ambos poderiam parecer semelhantes.

Isso significa que os mesmos **24 cenários oferecem 24 oportunidades para cada padrão**.

Essa simetria é ótima para a primeira engenharia.

# **8. Mas existe um problema: não podemos agrupar os itens na aplicação**

O usuário **não verá**:

PARTE 1 — PRC
PARTE 2 — DISC
PARTE 3 — TEMPERAMENTO

Isso contamina a resposta e torna o instrumento previsível.

Os 48 itens serão **intercalados**.

Algo conceitualmente assim:

PC → PRC → PC → DR → PC → PRC → DR → PC...

Além disso, evitaremos:

**três itens de conflito seguidos;**

**três perguntas com a mesma estrutura;**

**alternativa A representando sempre a mesma dimensão;**

**pares de consistência próximos.**

# **9. Randomização das alternativas**

Isso é importante para o futuro código.

No Banco Mestre, PC-001 poderá estar registrado internamente como:

**A = D
B = I
C = S
D = C**

Mas na tela o aplicativo poderá apresentar:

**C / A / D / B**

sem mudar a pontuação.

Ou seja:

**a posição visual da resposta não carrega significado psicométrico.**

Isso evita o usuário perceber:

“Ah, primeira alternativa sempre é dominante.”

Fundamental.

# **10. Porém, não randomizaria tudo indiscriminadamente**

Em escalas ordenadas como:

**imediatamente → rapidamente → gradualmente → depois**

não podemos embaralhar as alternativas.

A ordem possui significado.

Portanto:

### **PC escolha categórica**

Pode randomizar.

### **PRC escolha categórica**

Pode randomizar.

### **DR ordinal**

**Não randomizar.**

Essa regra já precisa existir na arquitetura do software.

# **11. Pares de consistência**

Quero inicialmente algo como **6 pares**, espalhados pelo instrumento.

Não são perguntas idênticas.

Exemplo:

### **PC-001**

decisão importante com informação incompleta.

Muito depois:

### **PC-023**

oportunidade com potencial e incerteza.

Ambos tangenciam relação com incerteza/decisão.

Outro:

### **PC-007**

recebe liberdade.

versus

### **PC-027**

percebe acompanhamento excessivo.

Ambos tangenciam autonomia, mas por ângulos diferentes.

Outro:

### **TH-002**

persistência depois de conversa difícil.

versus

### **TH-015**

persistência depois de conflito resolvido.

Muito bons.

# **12. Mas cuidado: consistência não significa igualdade**

Isso precisa entrar no algoritmo.

Se alguém responder:

PC-007 → forte autonomia.

PC-027 → não se incomoda com acompanhamento.

Isso não significa automaticamente:

“Mentiu.”

Talvez goste de autonomia, mas não interprete acompanhamento como ameaça.

Portanto, o Índice de Consistência não será:

respostas iguais = bom; diferentes = ruim.

Será baseado em **padrões de convergência entre múltiplos itens**.

Uma divergência isolada não significa praticamente nada.

**Este instrumento não avalia inteligência, caráter, competência profissional ou saúde mental.**

Excelente desde o primeiro piloto.

# **16. Captura de tempo — invisível**

O software futuramente deve armazenar:

**hora de início;**

**hora de término;**

**tempo por item.**

Não para dizer:

“Você demorou 12 segundos, portanto é C.”

Isso seria absurdo.

Mas para detectar:

**questionário respondido rápido demais;**

**abandono;**

**itens que exigem tempo excessivo;**

**problemas de compreensão.**

O tempo serve para **avaliar o instrumento**, não para diagnosticar personalidade.

Essa distinção é importantíssima.

# **17. Permitir voltar para alterar resposta?**

No piloto, eu permitiria.

E registraria anonimamente:

resposta inicial → resposta final.

Isso pode nos mostrar perguntas nas quais as pessoas frequentemente ficam em dúvida.

Se 40% dos respondentes alterarem PC-017, existe alguma coisa ali que merece investigação.

Mais um dado para a qualidade do instrumento.

# **18. Depois das 48 perguntas, NÃO mostrar resultado imediatamente no primeiro piloto**

Aqui eu faria algo diferente da versão comercial.

# **AUTOAVALIAÇÃO PÓS-INSTRUMENTO**

Sem mostrar resultado.

Não prova validade.

Mas gera informação.

# **21. O que NÃO faremos depois das primeiras dez respostas**

Isso é muito importante:

Não vamos olhar para você e dizer:

“Alisson é claramente X, então precisamos mexer na pergunta para o algoritmo dizer X.”

Esse seria um erro gravíssimo.

Seu conhecimento sobre si mesmo será **uma fonte de evidência**, não o gabarito do instrumento.

Da mesma maneira, eu não usaria meu conhecimento prévio sobre os mentees para “ajustar” o teste até ele produzir aquilo que esperamos.

O instrumento precisa ter oportunidade de **nos contrariar**.

# **22. Quando poderemos dizer “MGH validado”?**

Não logo depois do piloto.

O caminho será:

**validade de conteúdo**→ os itens representam adequadamente os construtos?

**processo de resposta**→ as pessoas interpretam como imaginávamos?

**estrutura interna**→ as respostas apresentam relações coerentes com nossa estrutura proposta?

**relação com outras variáveis**→ aparecem relações esperadas ou discriminantes quando comparadas a outras medidas?

**confiabilidade/precisão**→ quão estáveis/consistentes são determinadas medidas?

Esse é exatamente o tipo de etapa em que posteriormente quero um psicometrista conosco.

# **ETAPA 2.7 — agora vem a matemática**

É o próximo passo que eu considero mais delicado desde que começamos.

Precisamos transformar:

**48 respostas**

em:

**PRC™**Visual / Auditiva / Cinestésica

**PC**Dominância / Influência / Estabilidade / Conformidade

**DR™**Velocidade / Impacto / Persistência / Externalização

e depois determinar:

**predominância; proximidade; equilíbrio; intensidade relativa; consistência; confiança interpretativa.**

Só depois poderemos construir o:

# **MOTOR DE GOVERNO™**

E aqui vou defender uma regra importante:

**O Motor de Governo não deve ser uma IA recebendo as respostas e “inventando” uma interpretação.**

A inteligência artificial poderá futuramente **personalizar a linguagem**, mas o núcleo interpretativo precisa possuir **regras determinísticas, documentadas e versionadas**.

Assim, duas pessoas com exatamente os mesmos dados-base recebem a mesma lógica diagnóstica, independentemente de como a IA “acordou” naquele dia.

Isso será importantíssimo quando transformarmos o MGH em software.

**É para a engenharia matemática do MGH Piloto 1.0 que eu seguiria agora.**

Vamos. Aqui eu quero separar **matemática do Piloto** de **matemática definitiva**. No Piloto 1.0, precisamos de um sistema coerente, reproduzível e auditável — mas que assuma explicitamente que pesos, cortes e regras ainda são hipóteses a serem confrontadas com dados.

# **ETAPA 2.7 — ENGENHARIA MATEMÁTICA DO MGH™ PILOTO 1.0**

A primeira decisão é esta:

**As três lentes não terão a mesma matemática só para o sistema parecer uniforme.**

PRC™, PC e DR™ medem coisas de naturezas diferentes. Forçar uma fórmula única seria elegante no código e ruim metodologicamente.

Teremos três motores de pontuação independentes:

**PRC → preferência relativa + intensidade declarada
PC → distribuição comportamental relativa
DR → posição em quatro eixos ordinais**

Somente **depois** os resultados serão cruzados pelo Motor de Governo™.

# **1. Uma regra fundamental: resposta bruta nunca vira interpretação diretamente**

Teremos quatro camadas:

**RESPOSTA → ESCORE BRUTO → ESCORE DA LENTE → INTERPRETAÇÃO → MOTOR DE GOVERNO**

Exemplo:

PC-001 = alternativa A

não significa diretamente:

“Essa pessoa precisa de autonomia.”

Significa inicialmente apenas:

PC-001 → D → +1 ponto na chave daquela versão.

Depois essa informação se combina com outras.

Isso impede que uma única resposta gere uma conclusão gerencial.

# **2. Matemática da PRC™**

Temos 12 itens.

Minha proposta para o Piloto:

**8 itens de escolha forçada + 4 itens de avaliação independente.**

## **Parte A — Escolha forçada**

Cada item contém:

V = Visual
A = Auditiva
C = Cinestésica

Escolheu uma alternativa:

**+1 para aquela dimensão.**

Ao final poderíamos ter:

V = 5
A = 2
C = 1

Como são 8 escolhas:

**V = 62,5% das escolhas
A = 25%
C = 12,5%**

Mas não chamaremos isso de:

“Você é 62,5% visual.”

Chamaremos de:

**62,5% das escolhas forçadas favoreceram recursos visuais.**

A diferença semântica é enorme.

# **3. Parte B — Avaliação independente**

Nos quatro itens, cada pessoa avaliará três recursos em escala de 1 a 5.

Exemplo:

Visual = 5
Auditivo = 4
Cinestésico = 3

Em quatro situações, teremos quatro avaliações independentes de cada dimensão.

Calculamos inicialmente a média:

**Vᵢ = média das quatro avaliações visuais
Aᵢ = média das quatro avaliações auditivas
Cᵢ = média das quatro avaliações cinestésicas**

Resultado possível:

Visual = 4,75/5
Auditivo = 4,25/5
Cinestésico = 3,50/5

Isso significa algo diferente da escolha forçada.

E eu **não juntaria os dois números imediatamente**.

# **4. Por que não criar logo uma nota única PRC?**

Porque imagine:

### **Pessoa A**

Escolha forçada:

V = 75%

Avaliação independente:

V = 4,8
A = 4,7
C = 4,5

### **Pessoa B**

Escolha forçada:

V = 75%

Avaliação independente:

V = 4,8
A = 2,2
C = 1,8

As duas apresentam preferência relativa por V.

Mas a Pessoa A possui um repertório declarado muito mais multimodal.

Portanto o Piloto deve preservar:

### **PRC-P**

**Preferência relativa**

e

### **PRC-I**

**Intensidade declarada de utilidade**

Depois os dados nos dirão se vale combiná-las.

# **5. Poderemos descobrir algo muito interessante**

Em vez de apenas:

Visual predominante

o MGH talvez consiga distinguir futuramente:

**Visual concentrado**versus
**Visual multimodal**

Isso é muito mais útil para gestão.

Porque:

“Prefere estrutura visual, mas responde bem também à explicação verbal”

é diferente de:

“Apresenta preferência visual muito mais pronunciada que as demais formas avaliadas.”

Mas **não criaremos esses rótulos agora**.

Primeiro queremos observar se os dados justificam essa distinção.

# **6. Matemática dos Padrões Comportamentais — PC**

Aqui temos 24 itens categóricos.

Cada item possui uma alternativa associada primariamente a:

**D | I | S | C**

Na versão mais simples do piloto:

alternativa escolhida = **1 ponto** para o padrão correspondente.

Portanto:

**D + I + S + C = 24**

Exemplo:

D = 9
I = 7
S = 3
C = 5

Podemos representar internamente:

D = 37,5% das escolhas
I = 29,2%
S = 12,5%
C = 20,8%

Novamente:

Isso **não significa**:

“Essa pessoa é 37,5% dominante.”

Significa:

naquela versão do instrumento, 37,5% das escolhas comportamentais foram classificadas na chave D.

# **7. Inicialmente, todos os itens terão peso 1**

Isso é deliberado.

Não vamos decidir:

PC-001 vale 1,7
PC-008 vale 0,8

com base em nossa intuição.

No Piloto:

# **peso = 1.**

Posteriormente, dados podem mostrar que determinados itens discriminam melhor ou representam melhor determinado fator.

Só então discutiremos pesos.

Essa é uma regra que quero congelar:

**Nenhum item recebe peso superior apenas porque nós gostamos mais dele.**

# **8. Mas teremos uma segunda camada interna: FACETAS**

Embora PC-001 dê +1 para D quando determinada alternativa é escolhida, armazenaremos também:

dimensão = D
faceta = velocidade decisória
contexto = decisão.

Então poderemos observar posteriormente:

**D apareceu em decisão?
D apareceu em conflito?
D apareceu em autonomia?
D apareceu sob pressão?**

Isso permite distinguir:

**escore alto concentrado**

de

**escore alto transversal.**

Essa informação poderá se tornar extremamente valiosa.

Mas no Piloto 1.0:

**não entra ainda na nota principal.**

Serve para análise.

# **9. Não teremos “perfil principal” simplesmente pelo maior número**

Suponha:

D = 8
I = 7
S = 4
C = 5

Seria simplista dizer:

Perfil D.

D e I estão praticamente juntos.

Então precisamos calcular:

# **DISTÂNCIA ENTRE DIMENSÕES**

Ordenamos:

P1 = maior escore
P2 = segundo
P3 = terceiro
P4 = quarto

E calculamos:

**Δ12 = P1 − P2**

Exemplo:

D = 9
I = 8

Δ12 = 1.

Isso indica **proximidade**, não predominância clara.

Outro:

D = 13
I = 5

Δ12 = 8.

Agora temos uma concentração muito diferente.

# **10. Mas não vou inventar agora que “diferença de 3 = predominância”**

Isso seria justamente o que estamos tentando evitar.

No Piloto armazenamos o **gap bruto**:

0, 1, 2, 3...

Depois observamos sua distribuição na amostra.

Só posteriormente poderemos definir faixas como:

muito próximas
moderadamente diferenciadas
fortemente diferenciadas.

Esses cortes precisam surgir de dados e utilidade interpretativa.

# **11. Entropia comportamental — uma possibilidade interessante**

Existe uma medida matemática que poderá nos ajudar posteriormente a representar quão distribuídas estão as escolhas entre D/I/S/C: **entropia**.

Sem transformar o relatório numa aula de estatística, ela permitiria distinguir:

Pessoa A:

de

Pessoa B:

15 / 3 / 3 / 3.

A primeira apresenta distribuição muito uniforme.

A segunda, concentração muito maior.

Por enquanto:

**calculamos para pesquisa, mas NÃO interpretamos para o usuário.**

Quero armazenar esse indicador no piloto para estudá-lo depois.

# **12. Matemática da DR™ — Dinâmica de Reação**

Aqui a lógica muda completamente.

Temos:

**Velocidade
Impacto
Persistência
Externalização**

Três itens por eixo.

Cada alternativa possui ordem.

Exemplo velocidade:

A = reação muito rápida
B = rápida
C = gradual
D = mais tardia.

Internamente podemos codificar:

**A = 4
B = 3
C = 2
D = 1**

Então três itens poderiam gerar:

4 + 3 + 4 = 11

Intervalo possível:

**3 a 12.**

Mas para facilitar armazenamento/comparação podemos transformar linearmente para uma escala **0–100**.

Assim:

mínimo possível → 0
máximo possível → 100.

Um escore bruto 11/12, por exemplo, não seria simplesmente “91,7%”; fazemos a transformação considerando o piso da escala. No caso de três itens 1–4:

**(11 − 3) / (12 − 3) × 100 ≈ 88,9**

Isso representa **posição na escala construída**, não “88,9% de velocidade emocional”.

# **13. Direção das quatro escalas**

Precisamos congelar a semântica:

### **Velocidade**

0 = reação mais gradual
100 = reação mais imediata

### **Impacto**

0 = menor impacto funcional percebido
100 = maior impacto funcional percebido

### **Persistência**

0 = reação tende a dissipar mais rapidamente
100 = tende a permanecer por mais tempo

### **Externalização**

0 = menos perceptível externamente
100 = mais perceptível externamente

Isso evita ambiguidades no código.

# **14. Não existe “melhor lado”**

Isso precisa estar no DNA matemático.

**100 de velocidade não é melhor que 30.**

**20 de externalização não é mais maduro que 80.**

**90 de persistência não é defeito.**

São descrições relativas ao padrão de respostas.

Portanto:

**o MGH não utilizará vermelho para “baixo” e verde para “alto” nessas dimensões.**

Alto ≠ bom.

Baixo ≠ ruim.

Isso também influenciará o design futuro.

# **15. DR e Temperamentos Históricos**

Eu NÃO transformaria imediatamente os quatro eixos em:

# **DR = [V, I, P, E]**

Depois, numa camada separada, poderemos calcular **proximidade histórica** com quatro protótipos.

Conceitualmente:

Colérico → velocidade alta, impacto alto, externalização alta, persistência moderada/alta.

Sanguíneo → velocidade alta, impacto relativamente alto, externalização alta, persistência menor.

Fleumático → velocidade menor, impacto menor/moderado, externalização menor, estabilidade.

Melancólico → velocidade mais gradual, impacto interno relevante, externalização menor, persistência alta.

Mas esses protótipos ainda precisam ser operacionalizados.

Portanto:

# **NÃO entram na pontuação do Piloto 1.0.**

Ficam como **hipótese posterior de interpretação histórica**.

Essa decisão protege o instrumento.

O Motor trabalhará com **convergências**.

# **22. Podemos criar níveis de evidência**

Isso pode se tornar uma característica fantástica do sistema.

### **E1 — SINAL**

Uma lente sugere algo.

Não gerar recomendação forte.

### **E2 — CONVERGÊNCIA**

Duas evidências independentes apontam na mesma direção.

Permite hipótese gerencial.

### **E3 — CONVERGÊNCIA FORTE**

Múltiplos indicadores + consistência suficiente + presença em diferentes contextos.

Permite recomendação mais assertiva, ainda sem tratar como verdade absoluta.

Assim o próprio sistema sabe:

**quanto pode afirmar.**

Isso é muito superior a gerar textos categóricos para qualquer resultado.
